A three-minute primer: markdown, since every file today is one

spec.md, constitution.md, tasks.md, all of it is plain text with a few symbols. Here's the whole syntax you need.

# Heading one
## Heading two

**bold** and *italic* text

- A bullet point
- Another bullet point
1. A numbered step
2. Another step

`inline code`
[link text](https://example.com)

That's the whole syntax

  • # and ## make headings, more #'s means a smaller heading
  • ** ** for bold, * * for italic
  • - or a number starts a list
  • Backticks for `code`, three backticks for a whole code block
No app required. Any text editor writes it, and every AI agent today reads and writes it natively, it's why Spec Kit picked it for spec.md, constitution.md and tasks.md.

Part one

Describing software instead of writing it

You steer with language; the agent produces the code. Here's where that genuinely works and where it doesn't.

Where it genuinely wins

  • Speed to something visible. Idea to clickable screen in minutes
  • Throwaway work. Prototypes, demos, one-off tools, pitch assets
  • Exploration. Five layouts cost five prompts, not five days
  • Front-end UI. Models are strongest exactly where a demo lives

Where it collapses

  • Around screen three. New output contradicts old output
  • On edits. "Fix the header" silently rewrites the checkout flow
  • On anything stateful. Auth, payments, data integrity, permissions
  • On handoff. Nobody, including you, knows what was intended
Vibe coding is ungoverned, not broken. The chat log is not a specification.
Fast for demos, fragile for productsPart one
Part one

Why prompt-only breaks at screen three

The model isn't forgetting your product. It never had it in the first place.

The symptom

Colours drift. Button styles change. The nav loses a link. A screen you liked yesterday comes back different today.

The cause

Every prompt is a fresh negotiation. Your decisions live in your head and in scrollback, never in a file the agent reads before it writes.

The cure

Put the decisions in a document and make the agent read it every time. That document is the spec, and that is the whole of spec-first.

This is why your AI Studio prototype held together: one chat, one session, the constitution still in view. Open a fresh chat tomorrow and none of it exists. Treat the AI as a contractor who arrives each morning having read the brief and nothing else, then write a brief good enough for that contractor.

Spec-Driven Development

SDD is the method: the spec is the source of truth, and code is generated from it. Five phases.

01
Constitution

Non-negotiable rules. Stack, design language, tone, what must never happen.

02
Spec

What the product does. Users, screens, flows, states, the what and why, no tech.

03
Plan

The how. Structure, files, data shapes. Written by the agent, approved by you.

04
Tasks

The plan sliced into small units, each independently checkable.

05
Implement

The agent builds task by task. You review against the spec, not against your mood.

You've run a version of this already, paper, prompt, prototype, prove, pass. What changes: the prompt becomes a document that outlives the chat, and the checkpoint between every phase is you.

├── plan.md

Before you write anything: make the folder

A chat holds one file in its head. A folder holds a project.

lunch-app/
├── .specify/memory/constitution.md   rules
├── specs/001-lunch-preorder/
│   ├── spec.md             what & why
│   ├── plan.md             how
│   └── tasks.md            the work
├── index.html              the build
├── versions/                builds that worked
├── research/                notes, refs
└── video/                   script, renders

Why this unlocks the next tier of tools

  • AI Studio holds one conversation and one file. You paste in, you copy out
  • Antigravity, Codex, Claude Cowork read the whole folder, cross-referencing spec against build
  • That's how an agent can say "your spec promises a pickup code and your HTML has no screen for it"
  • It's also why HyperFrames can render your prototype: the .html is in the folder it's working in
Do this today even if you never leave AI Studio. Moving to an agent later is copying a folder, not rebuilding a project.

Part three

Four moves that make one static file feel like a real product

Your current prototype navigates but holds placeholder content. These four moves are the difference.

Data as a variable

A JS array at the top of the file holds your records. It behaves like a database for the length of a demo.

Fake the latency

Add a 400ms delay and a loading state. Instant responses feel fake; a short wait reads as talking to a server.

Real-looking data

Khmer names, local prices, plausible timestamps. Specificity makes a demo believable.

One golden path

Make one route through the app flawless. Anything off it can be "coming soon."

Build this as ONE self-contained HTML file. No backend, no build step, no external APIs.
All data lives in a JS array at the top of the file, clearly marked MOCK_DATA.
Simulate network calls with a 400ms delay and a loading state.
Every screen in the spec must be reachable by clicking. Nothing else should exist.

When the AI breaks your demo

Small, surgical prompts. Never "fix everything."

When this happensSay exactly this
The style driftedRe-read the constitution section of my spec. Apply it to the whole file. Change nothing else.
It rewrote working screensOnly modify the checkout screen. Return the complete file with every other screen byte-identical.
A button does nothingThe confirm button on screen three has no handler. Wire it to navigate to screen four.
It invented featuresYou added a settings page. It's in my out-of-scope list. Remove it and everything that links to it.
It's now worse than beforeDiscard the last change. Go back to the previous version and make only this one edit.
You've lost the threadStart a fresh chat. Paste the spec and the last working file. Never argue a confused agent back to sanity.
Save a copy of the file every time it works. "Working version" beats "latest version" every single time.

Part four

Front-end mistakes look wrong. Backend mistakes lose data.

The tools are one thing. The reason the rules change here is another.

Agentic environments

  • Antigravity, agent-first IDE, Gemini-powered
  • Claude Code, terminal agent that reads your whole project
  • Cursor, an AI-native editor
  • GitHub Copilot, agent mode inside VS Code

Backend in a box

  • Supabase, Postgres, auth, storage, APIs
  • Firebase, realtime database, auth, hosting
  • PocketBase, a single-file backend

Why it's harder

  • Bugs are invisible, no screen shows you the problem
  • Mistakes are permanent, corrupted data doesn't undo
  • Security failures stay silent until they don't
Vibe-code the front-end freely. For the backend, go spec-first with a real reviewer. Never ship AI-written auth, payments or personal-data handling without an engineer reading it.

Three things that will catch you out

  • The file must be named index.html
  • Every deploy URL is public, no private mock data
  • Test the live link on a phone before you send it

Turning the link into a QR code

Don't ask an image model to draw one. It'll produce a convincing picture that doesn't scan.

uv run --with "qrcode[pil]" python -c \
"import qrcode; qrcode.make('https://…').save('qr.png')"

Why bother

A link opens on any laptop or phone, no download, no "which browser". Your submission can't be the version that only worked on your machine.
